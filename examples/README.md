# Domain Vocabulary Seeding -- Physics

Demonstrates the LIRA Vocabulary Layer's existing domain-seeding
capability (`DictionaryProcessor.identify_word`, `PartOfSpeechIdentifier`,
`AsyncDictionaryHydrator`, `ExternalDictionaryAdapter`) against a
supplied domain ("Physics") and a representative source text. No
Vocabulary Layer class is modified for this demonstration -- it drives
the pipeline exactly the way any other Domain is seeded (see
`vocabulary/documentation/README.md`, 9.6).

## Network caveat

This sandbox's network policy rejects outbound calls to
`api.dictionaryapi.dev` -- the only external provider
`AsyncDictionaryHydrator` is wired to -- with a confirmed 403 policy
denial, not a transient failure. A live call genuinely cannot be made
from this environment.

`physics_domain_seeding.py` therefore patches `urllib.request.urlopen`,
for the duration of the script only, to serve `physics_domain_seeding_fixtures.py`'s
hand-written responses -- in that API's own real response shape --
instead of making a live call. Every other line of the real pipeline
runs completely unmodified: `ExternalDictionaryAdapter.parse_api_payload`
parses the exact same JSON shape a live response would have, ranks
candidates by the same domain-relevance formula, and
`AsyncDictionaryHydrator` creates `Word`s from the result exactly the
way it would from a live response. The fixture set is also
deliberately incomplete -- neither `branch` nor `studies` originally
had an entry, so the demonstration also exercises the genuine "no
evidence -> stays unresolved, not guessed" path, the same way a real
404 would. `branch` has since been promoted into the Common Vocabulary
Cache itself (Definition-gap vocabulary below), so it now resolves
immediately from the Common seed before hydration is ever attempted;
only `studies` still demonstrates this path.

`ExternalDictionaryAdapter`'s `source_references` still label every
hydrated Word `"Free Dictionary API"` -- that's genuinely which live
provider this code is wired to call in production, and changing that
label was out of scope for this demonstration. The generated example
UI's page title says explicitly that this run's data came from
curated fixtures standing in for that API, so nobody reading the UI on
its own is misled about what actually happened.

## Result

- 119 unique tokens across a 23-sentence source text.
- 77 distinct lexical forms newly hydrated, becoming 95 `Word` records
  -- many with more than one part of speech from a single lookup
  (`charge` -> NOUN + VERB, `current` -> ADJECTIVE + NOUN, `field` ->
  NOUN + VERB, `force` -> NOUN + VERB, and more), demonstrating the
  core requirement: every externally-evidenced part of speech is
  hydrated, not only the one used in the source sentence.
- Domain-relevance ranking correctly preferred the Physics-flavoured
  sense over the general one everywhere both existed in the fixture
  data (`field` -> "a region... a physical quantity... has a value",
  not "an area of open land"; `current` -> "the rate of flow of
  electric charge", not "a body of water"; similarly for `charge`,
  `power`, `force`, `wave`, `resistance`).
- 2 words (`branch`, `studies`) correctly left unresolved at the time
  -- no fixture evidence, reported rather than guessed. `branch` has
  since been promoted into Common (Definition-gap vocabulary below);
  rerunning this script today leaves only `studies` unresolved.
- Reprocessing the same text a second time added zero new words and
  made zero new successful external lookups -- confirmed duplicate
  prevention and vocabulary reuse.
- "Existing words enriched" was 0 by the script's own before/after
  part-of-speech tracking: none of the Physics content words happened
  to need an *additional part of speech* added to an already-seeded
  lexical form. See Word-sense conflicts below for a related but
  distinct case this tracking can't see -- a *same-part-of-speech*
  conflict, not a missing one.

## Word-sense conflicts found and resolved

Checking every fixture word against the Common seed directly (not
assumed) found 4 collisions: `object`, `depend`, `position`,
`particle` all already exist there. `identify_word()` only queues
hydration when *no* existing sense at all matches
(`PartOfSpeechIdentifier.identify_seeded`), so none of these four ever
reached `ExternalDictionaryAdapter` -- they silently kept whatever
Common already had.

For `depend`/`position` that's fine: Common's existing definitions
("to be determined, influenced, or controlled by something else"; "the
place where something is located") are perfectly good general-English
senses that also serve physics usage. But `object` and `particle` are
genuine conflicts -- Common's senses are unrelated *grammatical* terms
("the noun or pronoun that receives the action of a verb"; "a function
word that does not fit the main parts of speech"), seeded there as
metalinguistic vocabulary, not physics ones. Left unfixed, 5 of this
demonstration's own curated relationships (below) would have silently
attached to the wrong "particle" -- `matter`'s hyponym would have been
a part-of-speech term, not a subatomic particle.

Fixed via `DictionaryProcessor.register_conflicting_sense` --
`vocabulary/documentation/README.md`'s own pre-existing conflict-
resolution path (9.2) for exactly this situation, not a new mechanism.
`physics_domain_seeding.py`'s `_register_conflicting_senses` builds the
Word the normal way (`ExternalDictionaryAdapter.parse_api_payload` on
the fixture data, same as any other hydration) and registers it as a
second sense; `object`/`particle` are added to the Physics Dictionary,
`is_common=False`, keeping the identical `lexical_form` as Common's
original entries -- distinguished only by domain and by their own
`entry_id` (see Adding a stable entry_id per vocabulary entry below;
before that fix, this used to mangle `lexical_form` into `object_2`/
`particle_2` instead). Idempotent (checked directly): a second run
registers nothing new.

## Relationships among hydrated words

`RelationshipSeeder` only runs once, at Domain creation, against the
static `assets/common/en/relationships/*.json` files -- it never
relates a word added later by hydration. Confirmed directly before
fixing it: the first version of this demonstration hydrated 81 words
and none of them had a single `LexicalRelationship`.

`physics_domain_relationships.py` now hand-curates 45 pairs, covering
every `LexicalRelationshipType` Lexical Semantic kind with at least 5
genuine examples, resolved by exact `(text, part_of_speech)` (several
are homographs) and seeded via
`domain.vocabulary.lexical_relationship_processor.create` directly --
the same primitive `RelationshipSeeder` itself is built on:

| Kind | Pairs | Edges | Example |
|------|-------|-------|---------|
| HYPERNYM / HYPONYM | 10 | 10 + 10 | `matter` hypernym-of `particle`; `physics` hypernym-of `mechanics`, `thermodynamics` |
| SYNONYM | 5 | 10 | `net` ↔ `total`; `possess` ↔ `have`; `velocity` ↔ `speed` |
| ANTONYM | 5 | 10 | `hot` ↔ `cold`; `closed` ↔ `open`; `kinetic` ↔ `potential` |
| MERONYM / HOLONYM | 6 | 6 + 6 | `nucleus` part-of `atom`; `proton`/`neutron` part-of `nucleus`; `crest` part-of `wave` |
| TROPONYM | 5 | 5 | `move` → `flow`/`spin`/`wave`/`transfer`/`accelerate` (specific manners of moving) |
| ENTAILMENT | 5 | 5 | `accelerate` entails `move`; `possess` entails `have` |
| CAUSE | 5 | 5 | `heat` causes `melt`/`expand`; `exert` causes `accelerate` |
| RELATED | 4 | 8 | `particle` ↔ `wave` (duality); `electric` ↔ `magnetic` |

**RELATED is deliberately the smallest set** -- 4 pairs, fewer than
every other kind -- used only where a genuine connection exists but no
more specific kind fits (kept out of RELATED and reclassified where a
better fit existed: `kinetic`/`potential` -> ANTONYM,
`net`/`total` -> SYNONYM, most of `matter`/`particle`/`property`'s
network -> HYPERNYM/HYPONYM). It is the lowest-priority kind, not a
default.

Directional conventions (HYPERNYM vs. HYPONYM, MERONYM vs. HOLONYM)
were verified against `Word.py`'s own derived properties before
seeding anything -- `meronyms()`/`holonyms()` read *incoming* edges,
`hypernyms()`/`hyponyms()`/`troponyms()` read *outgoing* ones -- and
re-confirmed after seeding by calling `particle.hyponyms()`,
`electron.hypernyms()`, `atom.meronyms()`, `nucleus.holonyms()`, and
`move.troponyms()` directly and checking each returned the right word.
See `physics_domain_relationships.py`'s module docstring for the full
reasoning.

physics_source_text.py's second paragraph (atom/nucleus/proton/
neutron/electron, melt/expand/attract, open/inverse/stationary, apply,

## Definition word breakdown

`Word.definition_words(dictionary)` (`vocabulary/documentation/README.md`,
4.4) breaks a Word's own `definition` text into its own sequenced array
of `DefinitionWordReference`s -- one per token, in reading order,
resolved against the Dictionary domain-first (preferring a non-common
sense, the same one-liner already used to resolve the relationship
pairs above). A token with no match at all resolves to `word=None`,
reported rather than guessed. Not a new pipeline stage: it's a derived
property in the same family as 4.3's `synonyms`/`hypernyms`/etc., just
resolved against the Dictionary directly instead of a
`LexicalRelationshipStore`, since a definition is prose about a Word,
not a claimed relationship between two Words.

`DictionaryProcessor.queue_definition_hydration(word)` (9.7) closes this
into a loop: it walks `definition_words()` and queues external
hydration -- the same `AsyncDictionaryHydrator.queue_hydration` path
`identify_word` itself uses -- for every unresolved reference. An
unresolved definition word is treated as a discovery signal (what to
hydrate next), not a defect blocking the property's usefulness.

`physics_definition_completeness.py` prototypes both against the same
648-word Physics Domain seeded above:

- **Completeness**: 97 hydrated/conflict-registered Physics Words carry
  a `definition`, totalling 1185 definition tokens; 812 (69%) resolve
  against this Domain's Dictionary, 373 (31%) don't. Only 1 Word's
  definition (`stationary`) is fully self-contained; every other one has
  at least one gap -- expected, since `examples/physics_domain_seeding_fixtures.py`
  was curated for the Physics source text's own ~119-token vocabulary,
  not for exhaustive coverage of every word any dictionary definition
  happens to use (`measured`, `physical`, `amount`, `motion`, `space`,
  `subatomic`, and 257 more distinct tokens appear in at least one
  definition and resolve nowhere).
- **Recursive discovery**: `successive` ("Following one after another;
  consecutive.") is the most tractable Word with a gap -- one unresolved
  token, `consecutive`. Calling `queue_definition_hydration(word)` on it
  queues `consecutive` through the real (fixture-patched, per the
  Network caveat above) hydration path and drains the queue; `consecutive`
  has no fixture entry, so it stays unresolved after the round -- the
  same honest "no evidence -> stays unresolved, not guessed" outcome
  the original seeding demonstration's `branch`/`studies` already
  established, just reached through a definition instead of a sentence.
  Against the real Free Dictionary API in production, most queued gap
  words would resolve; this sandbox's fixture set was never meant to
  cover them, so this round mostly proves the wiring fires correctly,
  not that every gap closes on the first pass.

This distinguishes two things the domain-seeding work above already
established, applied to definitions instead of sentences: `identify_word`
resolves *sentence* occurrences against the Dictionary, one word at a
time as a document is tokenized; `definition_words` resolves the prose
*inside* a Word's own definition the same way, on demand, letting a
caller measure how self-contained a Domain's vocabulary actually is and
decide what to hydrate next from the gaps it finds -- reusing
`identify_word`'s own hydration queue rather than inventing a second one.

The 262 words this measurement found unresolved are acted on next, not
left as a static report -- see Definition-gap vocabulary below.

## Verb nominalisation

`NOMINALISATION` (`vocabulary/documentation/README.md`, 6.2.1
Derivation) has been part of `LexicalRelationshipType` since it was
first defined, documented with its own example ("decide" -> "decision"),
but never actually seeded anywhere until now.
`verb_nominalisation_vocabulary.py` works through every base-form
`VERB` Word already seeded -- Common and Physics, but only true
lemmas: a verb that already has an outgoing `LEMMA_FORM` edge (an
inflected surface form like `causing` or `determined`) is skipped, since
nominalising a 3rd-person or participle form rather than its lemma
would be linguistically wrong -- and classifies each: does it have a
genuine, standard-English nominalisation, or not?

96 Common and 30 Physics base verbs were checked. 36 Common pairs and 7
Physics pairs qualified (`achieve` -> `achievement`, `identify` ->
`identification`, `exist` -> `existence`, `possess` -> `possession`,
...); the rest were deliberately left alone, not forced:
zero-derivation verbs where the noun sense is the *same* word, not a
distinct derived form (`change`, `measure`, `pull`, `push`, `force`,
`heat`, `wave`, `work`, and more -- `NOMINALISATION` means a derived
form, matching its own documented example); grammar/logic-operator
verbs with no natural English nominalisation (`and`, `or`, `not`,
`xor`, `xnor`, `nand`, `nor`, `plus`, `minus`); and verbs with no
single, standard, non-forced nominalisation (`be`, `have`, `do`,
`become`, `bring`, `follow`, `join`, `make`, `happen`, `reach`, and
more). 4 of the 43 target nouns already existed (`movement`, `passage`,
`reference`, `relation`, `acceleration` -- several from the
definition-gap batch above); the other 39 were promoted (Common) or
hydrated (Physics), the same two-tier mechanism as that batch. Every
pair gets two edges, the Common relationship cache's own established
convention: (verb, `NOMINALISATION`, noun) plus the reciprocal (noun,
`LEMMA_FORM`, verb).

One planned pair surfaced a real bug instead of a clean relationship.
`cause` -> `causation` is a genuine nominalisation, but `cause` is a
Common homograph (`NOUN` and `VERB`, both open-class -- the `NOUN`
sense, in `metalinguistic_nouns.json`, loads before the `VERB` sense,
in `metalinguistic_verbs.json`). `RelationshipSeeder.seed_domain`
resolves a static cache entry's `source_lexical_form` via
`Dictionary.lookup()` -- first-seeded-wins by text alone, not
part-of-speech-aware -- so a cache entry naming `cause` as source can
only ever attach to the `NOUN` sense. Checking the actual resulting
edge (not assuming) confirmed it. Checking the rest of the cache for
the same failure mode found one more, pre-existing since the
definition-gap batch: `cause` -> `causing` (`PRESENT_PARTICIPLE_FORM`)
had the identical problem, silently attached to the `NOUN` sense the
whole time. Both `cause`-involving pairs (4 edges total) were removed
rather than left wrong; `causing` and `causation` keep their own
accurate definitions (each already states the relationship in prose),
just without the formal graph edge. Surfaced, not fixed: making
`seed_domain`'s resolution part-of-speech-aware would be a change to a
shared pipeline class, well beyond this batch's scope -- see
`assets/common/en/relationships/README.md`'s own Version section for
the exact edges removed and the full reasoning.

## Fixing the relationship cache's own POS blind spot

`RelationshipSeeder.seed_domain` had the identical part-of-speech blind

## Adding a stable entry_id per vocabulary entry

A user-facing usability problem, not a bug in any Vocabulary Layer
guarantee: `register_conflicting_sense` (9.2's Strategy 3, used above
for `object`/`particle`) told two coexisting senses of the same
(text, part_of_speech) apart by mangling `lexical_form` into a
sense-numbered suffix -- `particle` / `particle_2` -- functionally
fine (`Dictionary.lookup_all` still finds both, `text` stayed
untouched), but a confusing thing to actually show someone reading
`DictionaryView`'s Words table, and the trigger for this batch: create
a real, stable identifier for each distinct (domain, part_of_speech,
lexical_form) vocabulary entry, store it in the asset files, and show
it in the UI instead of leaning on the suffix.

`Word` gains `entry_id` (`vocabulary/documentation/README.md`, 4.2) --
deliberately distinct from the pre-existing `uuid` field, which is a
per-Domain-graph-instance identity, regenerated every time a Word is
copied into a new Domain's Dictionary (`Dictionary.seed_from`,
`WordSeeder.seed_closed_class_words`) so that two Domains' independent
copies of "be" are never confused as the same graph node. `entry_id`
is the opposite: assigned once, when a Word is first authored, and
left untouched by every later copy -- the persistent Qualified Word
Identity a Common Vocabulary Cache entry keeps no matter how many
Domains end up holding their own runtime copy of it.

`WordSeeder` was extended to match: `_entry_to_word`/`_word_to_entry`
read and write `entry_id` verbatim, and `validate_assets()` now
requires it and checks it for global uniqueness across the entire
cache (`seen_entry_ids`, the same discipline already applied to
`(lexical_form, part_of_speech)`). `DictionaryProcessor.register_conflicting_sense`
was simplified to stop touching `lexical_form` at all -- both senses
now keep the identical, unmangled form, relying on `entry_id` (plus
the Domain pill the UI already showed) to stay distinguishable.
`Dictionary.next_available_lexical_form`/`find_by_lexical_form`,
which existed only to serve the old suffix mechanism, were removed as
dead code.

`word_entry_id_backfill.py` is the one-time migration: walks every
mandatory, supplementary, and promoted word file and adds a freshly
generated UUID to any entry missing one, idempotent (a second run
adds nothing). Physics Domain words don't need backfilling -- they're
hydrated at runtime from fixture data standing in for an external API
(`physics_domain_seeding_fixtures.py`), never loaded from a stored
cache entry in the first place, so they get their `entry_id` the same
way they already got their `uuid`: freshly generated by `Word`'s own
`default_factory` at construction time.

`DictionaryView` shows the new field directly: an "Entry ID" line in
the detail panel, right under the Domain/part-of-speech pills. Verified
directly, not assumed: loaded the full 838-word cache and confirmed
exactly 838 unique `entry_id` values; re-ran the full seeding chain and
checked the rendered UI in headless Chromium -- searching "particle"
now shows two visually-identical `particle` rows (one Common, one
Physics), each selectable, each showing its own distinct `entry_id` and
Domain pill in the detail panel, with no console errors; same for
`object`. Word and relationship counts are unchanged by this batch --
it adds a field, not new vocabulary.

Common Vocabulary Cache: 838 words (unchanged), 288 relationships
(unchanged). Physics Domain: 981 words (unchanged), 411 relationships
(unchanged).

## Common definition-gap vocabulary

The same technique Definition-gap vocabulary (above) applied to the
Physics Domain's own hydrated words -- breaking every word's
`definition` down into its own constituent words
(`Word.definition_words()`, 4.4) and checking which of those aren't
themselves seeded -- run instead against the Common Vocabulary Cache's

for 1011 words at once doesn't parallelise well as a single pass, so
the list was split into 8 roughly-equal chunks and handed to 8
subagents running in parallel, each grounded with real context (up to
3 existing Common definitions that used the word, pulled directly from
the live Dictionary, not guessed) and the same style calibration
(`measured`, `expressed`, `specified`, ...) already established in
this cache. All 1011 were covered, no duplicates, no gaps, no invented
meanings -- verified mechanically (a scripted diff against the
original word list, not eyeballed) before any of it touched the real

Classifying and relating those 1011 words surfaced two further
extensions, the same "found while relating the new words, not decided
in advance" pattern `common_core_vocabulary.py`'s bonus NOMINALISATION
nouns already established:

  explicitly (`"denotes"` -> "Third person singular of **denote**"),

- **23 homograph senses.** A base already promoted under one

1163 words in total (1011 + 129 + 23), all open-class except 3:

`OPEN_CLASSES`, so the seeding script's first real run rejected all
three outright. Hand-added directly to `prepositions.json`/

file" discipline `common_core_vocabulary_seeding.py`'s metalinguistic
step already established for supplementary files, now exercised for
mandatory ones too. Two more candidates, `non`/`semi` (bound prefixes,
`PartOfSpeech.OTHER`), were excluded outright rather than forced
anywhere -- `OTHER` is deliberately never seeded in this cache
(`word_seeder.py`'s own comment on the enum member), a policy this
batch is the first to actually run into rather than just document.
1158 words went through `WordSeeder.promote_word` (`promoted_words.json`
283 -> 1441); `total_lexical_forms` grew from 388 to 391 for the 3
mandatory additions.

Wiring the 391 `MORPHOLOGICAL_LINKS` pairs into the relationship cache
used the same `source_part_of_speech`/`target_part_of_speech`
disambiguator `relationship_cache_homograph_fix.py` introduced, always
explicit on both endpoints of both the specific edge and its
reciprocal `LEMMA_FORM` edge, not just where a base happens to already

## Common semantic completion

Completes Lexical Semantic (LexicalRelationshipType group 1) coverage
for every base-form open-class word in the Common Vocabulary Cache:
1095 words (492 NOUN, 289 VERB, 240 ADJECTIVE, 74 ADVERB) with no

chunk's words with their real seeded `definition` text, plus a
reference list of all 1095 valid words it was allowed to use as a

explicitly told that leaving a word with zero relationships is correct
and expected, forcing one is not). Each agent was also given the exact
stored direction convention for every kind (`HYPERNYM` is narrower-
>broader, `MERONYM` is part->whole, `TROPONYM`/`ENTAILMENT`/`CAUSE` are

reverse direction of a symmetric pair a different chunk had already

independently wrote "circumstance SYNONYM condition" -- both true, only
one direction gets stored). Zero were dropped for an invalid word,
part_of_speech, kind, or self-reference -- every one of the 14 agents'
self-verification held up under independent re-checking. A further
programmatic check confirmed no `HYPERNYM`/`MERONYM` pair had both
directions proposed (which would be a contradictory edge -- a word

has no cycle.

1307 relationships survive into `examples/common_semantic_completion.py`:
481 `SYNONYM`, 451 `RELATED`, 214 `HYPERNYM`, 122 `ANTONYM`, 24
`MERONYM`, 9 `TROPONYM`, 3 `CAUSE`, 3 `ENTAILMENT`. `examples/

## Polysemy split

Found while inspecting the DictionaryView Cyclic tab (`vocabulary/ui/
README.md`): a word's SYNONYM box would draw lines to relationships
that had nothing to do with the sense its synonym-neighbours shared,
because the word's own `definition` had quietly merged two or three
distinct dictionary senses into one Common Vocabulary Cache entry --
`period` (NOUN) merged "a length of time" and "the punctuation mark
that ends a declarative sentence"; `character` (NOUN) merged
"personality" and "a written symbol used in writing or printing"; and
eleven more words did the same, two of them ("charge", "positive")
three ways at once (physics/legal/price; general/mathematical/
electric).

A `WordSeeder.validate_assets()` invariant already forbade this
from being fixed by adding a second entry outright: two Common cache
entries sharing (lexical_form, part_of_speech) are a rejected
duplicate, on the (correct, still-true) theory that only
part_of_speech legitimately tells two senses of one spelling apart
(the `that` DETERMINER/PRONOUN pattern). A genuine polyseme -- same
spelling, same part_of_speech, still two real senses -- has no such
signal. `Word` gained a `domain_tag` field for exactly this case:
`None` for every ordinary word, or a string like `"symbol.common"`
naming a split-off sense's own HYPERNYM as a subdomain of `"common"`
when (and only when) that sense already has a genuine hypernym in the
cache -- left unset rather than invented for a sense with no fitting
one. `WordSeeder`'s uniqueness rule widened from `(lexical_form,
part_of_speech)` to `(lexical_form, part_of_speech, domain_tag)`
accordingly, and `RelationshipSeeder` gained matching
`source_domain_tag`/`target_domain_tag` spec fields (the same role
`source_part_of_speech`/`target_part_of_speech` already played for
homographs) so a relationship edge can say which specific sense it
means.

12 of the 13 words were genuine splits: one entry kept its original
`entry_id`, trimmed to one sense's definition, and a brand-new entry
was added per additional sense, with every relationship the original
merged entry carried moved to whichever sense actually owns it (not
duplicated onto both). `positive`/`negative` (ADJECTIVE)'s single
ANTONYM edge was rebuilt as one pair per matching sense-family
(numerical<->numerical, electric<->electric) instead. The 13th,
`times` (VERB), turned out not to be a real second sense at all: its
"; also the plural of time..." clause just duplicated the sense
`times` (NOUN) already has its own separate entry for -- a stray
leftover clause, fixed by deleting it rather than by creating a word
that would only have duplicated an existing one.

See `vocabulary/assets/common/en/README.md`'s Polysemous senses
section for the complete per-word table, `examples/
common_polysemy_split.py` for the drafted data (definitions, domain
tags, which relationships move where), and `examples/
common_polysemy_split_seeding.py` for the migration itself --
idempotent, and wired into `common_semantic_completion_seeding.py`'s
own `run()` as its first step (ahead of that script's own Physics
Domain build, so the Domain and the regenerated example UI both
reflect the split).

Common Vocabulary Cache: 2465 -> 2481 words, 6111 -> 6187
relationships.

## Known, pre-existing limitation surfaced (not fixed) by this exercise

`DictionaryProcessor.identify_word` only queues hydration when a token
has *no* existing seeded/hydrated sense at all
(`PartOfSpeechIdentifier.identify_seeded` returns an empty tuple). A
word that already has *some* sense will never be re-queried for an
additional externally-supported part of speech, even in a new domain
-- this is exactly what made `object`/`particle`/`depend`/`position`
collide with Common above. `register_conflicting_sense` is the correct
tool once a conflict is *known*, but nothing in the pipeline itself
*detects* one automatically; this demonstration only caught all four
because every fixture word was checked against Common directly, by
hand, before relying on it. Fixing the detection gap would be a small,
targeted change to `identify_word`'s control flow (not a data-model
change), left for a future task rather than folded into this one.

The Common definition-gap batch above hit the same gap a second way:
`wave`/`moving`/`flow` weren't checked against Physics up front (there
was no reason to, until Common gained new senses of them), so this
time the gap was caught retroactively -- by re-running
`physics_domain_seeding.py` after the fact and noticing previously-clean
relationship pairs start reporting "word or sense not found", not by
checking ahead of time. That's strictly weaker than catching it before
shipping (it depends on something downstream actually exercising the
missing sense), reinforcing rather than closing the gap this section
already describes.

## Linguistics Layer read path verification

Verifies the Linguistics Layer's new read-only sentence sequencing
capability -- `Phrase.read()`/`Clause.read()`/`Sentence.read()`, reached
in practice through `LinguisticController.read_sentence`/`read_text` --
against a live Common Domain (`LIRAHost`), never a mock. See
`linguistics/documentation/README.md` for the full developer
specification this exercises.

Two corpora, both defined in `linguistics_sentence_reading_corpus.py`:

- **Corpus A** -- sentences built from words verified, live, as absent
  from the seeded Common Dictionary (spec 7's unknown-word handling).
  These are reconstructed from words this project's own implementation
  record identified as unseeded while this feature was designed, not a
  claimed reproduction of any externally supplied test list -- a later
  context compaction removed that pasted text from the session. Per the
  same spec's own rule ("a test must not silently supply unseeded
  lexical data"), the runner never hard-codes which tokens are
  unseeded: it checks each one against the live Dictionary itself
  (the Precondition pass) and asserts `Sentence.read()`'s behaviour
  against that observed, current ground truth.
- **Corpus B** -- a fully-seeded control corpus (every word verified
  seeded before inclusion) exercising a valid simple declarative with a
  copula complement, an invalid no-predicate sentence (two individually
  valid phrases, no `VERB_PHRASE` predicate at all -- the same shape as
  the specification's own worked example), two ambiguous seeded words
  resolved to `NOUN` by determiner context, a `VERB_PHRASE` predicate
  plus an infinitive-phrase modifier plus an object,
  phrase-internal coordination forming one subject `NOUN_PHRASE`, and a
  prepositional-phrase modifier.

The runner also confirms `Dictionary.lookup_all` is unchanged by
reading (spec 24) -- resolving an ambiguous word for one sentence must
not disturb the seeded candidate set for that lexical form.

Two real bugs surfaced only by running this corpus against the live
Dictionary (not by reasoning about the grammar tables in the abstract),
both fixed as part of this work:

1. An unrestricted `NOUN`->`NOUN` self-loop in `NOUN_PHRASE`'s grammar
   (intended for unmarked compound nouns) was greedily swallowing an
   ambiguous `NOUN`/`VERB` word into the subject phrase instead of
   leaving it available as the clause's verb (e.g. "word use the
   state" read "word use" as one compound-noun subject). Removed --
   `NOUN`/`PROPER_NOUN` now continue only via `CONJUNCTION`
   (coordination), never a bare self-loop.
2. `ReadingScorer`'s rank_key had no tie-break preferring a longer,
   equally-valid phrase reading over a shorter one, so a coordinated
   "the meaning and the word" was read as just "the meaning", leaving a
   stray "and" (also seeded as `VERB`) to be misread as the predicate.
   Fixed with a `span_length` tie-break (maximal munch) plus a
   `candidate_rank_index_sum` tie-break (prefer `identify_word`'s own
   top-ranked seeded sense) that had been designed but never actually
   wired into `SequenceEngine.scoring_factors`.

## Sentence Reader UI

A local, interactive page for the read path -- paste any sentence and
see it read live, rather than only through a fixed corpus. `python3
examples/linguistics_sentence_reader_ui.py` (optionally `--host`/`--port`,
default `127.0.0.1:8765`) starts a stdlib-only `http.server`
(`src/lira/linguistics/ui/sentence_reader_server.py`) wrapping a live
Common `Domain`; open the printed URL in a browser.

Two panels, side by side:

- **Predicted structure** -- the one interpretation the state machine
  ranked highest and materialised: `Sentence` -> `Clause` ->
  subject/predicate/object/complement/modifiers -> `Phrase` -> words,
  each with its validation outcome, confidence, and any structured
  errors.
- **Full trace** -- for every token position, every one of the six
  `PhraseType`s `PhraseReader` attempted: whether the token's seeded
  part(s) of speech matched that type's required start state, every
  completed candidate it found (span, validation outcome, confidence,
  with the actual winner marked), or a plain-language reason when it
  found nothing (no start match, or a start matched but nothing
  completed before running out of valid continuations).

This is a genuinely live Python backend, not a client-side
reimplementation of the grammar -- the whole point of the trace is to
show real decisions `SequenceEngine`/`ReadingScorer` already made, not
a second, JS-side approximation of them (`linguistics/documentation/
README.md`, section 2's "one shared sequencing engine"). A request
reads through the same `LinguisticController.read_sentence` every other
caller uses, with an additional optional `trace` list threaded through
`PhraseReader.read`/`ClauseReader.read`/`SentenceReader.read`
(additive -- `trace=None`, the default, is unchanged behaviour for
every existing caller).

## Combined offline UI (LiraView)

A single, fully static HTML page combining the Vocabulary Dictionary
and the Linguistics Sentence Reader as two tabs of one page, so the two
UI surfaces can be shared, browsed, or archived offline together
instead of as two disconnected files. `python3 examples/lira_view_example.py`
regenerates it at `src/lira/knowledge/assets/example_ui/lira_view_example.html`
from the live Common `Domain`, using the fully-seeded Corpus B control
sentences (`linguistics_sentence_reading_corpus.py`) as the Sentence
Reader tab's offline example set.

The combiner itself is `LiraView` (`src/lira/knowledge/ui/lira_view.py`)
-- it lives under the Knowledge layer, not under Vocabulary's or
Linguistics's own `ui/`, because a page needing both `DictionaryView`
and `SentenceReaderView` would otherwise force one layer's `ui/` to
import the other's, breaking layer independence; `Domain` is already
the one place that composes Vocabulary + Linguistics + Knowledge, so a
combined UI is Domain-level, not layer-level. `LiraView` renders one
shared page shell (masthead, tab switcher, footer) and fills each tab
from `DictionaryView.render_fragment()` / `SentenceReaderView.render_fragment()`
-- each existing view's own `render()` output, sliced between paired
inert HTML/CSS/JS comment markers already embedded in its page template
(e.g. `/*@@STYLE_FRAGMENT_START@@*/` ... `/*@@STYLE_FRAGMENT_END@@*/`).
This is purely additive: the markers render as harmless comments, so
each view's own standalone `render()`/`save()` behaviour is completely
unaffected by being combinable.

Combining two independently-authored pages into one required two
structural fixes, both isolated to the combiner and the sentence reader
view rather than touching shared code:

- **CSS class collision** -- `DictionaryView` already used `.panel` for
  its tab-content sections; the sentence reader's own `.panel`/`.panels`
  (the predicted-structure/full-trace result cards) meant something
  different but shared the same selector. Fixed by renaming the
  sentence reader's classes to `.sr-panel`/`.sr-panels`.
- **JS global-scope collision** -- both views' scripts independently
  declare top-level `const POS_COLORS` (among other names); concatenated
  unscoped into one page this is a `SyntaxError`. Fixed by wrapping each
  view's extracted script in its own IIFE (`(function () { ... })();`)
  inside `LiraView`'s combined template, giving each its own closure so
  identical top-level names never collide.

### Offline degradation

The Sentence Reader tab keeps its free-text input in the combined page,
but there is no guarantee a live backend is reachable once the page is
saved and shared as a static file -- so the same page and the same JS
have to behave correctly in three different situations, all backed by
one shared `render_page()` template in `sentence_reader_server.py` (also
used by the live server itself, so there is never a separate "offline
version" of the UI to drift out of sync):

- **Live server reachable** -- `fetch("/api/read")` returns a real
  result; renders normally.
- **Opened as a bare `file://` page** -- the browser blocks the
  cross-origin fetch outright (it throws); falls back to the embedded
  offline example set.
- **Served by a generic static file server** (e.g. `python3 -m http.server`,
  as opposed to the purpose-built `SentenceReaderServer`) -- `fetch()`
  does not throw (an HTTP error status doesn't reject the fetch promise),
  but the response body isn't the expected JSON shape; this is handled
  by the same fallback path rather than a separate, more confusing error.

In every fallback case, if the typed sentence matches one of the
embedded offline examples it renders that example's real predicted
structure and full trace (pulled from the same `/api/read` JSON shape,
precomputed at generation time via `build_examples()`); otherwise it
shows a plain-language banner explaining that no live server answered
and pointing at the example sentences below, or at running
`examples/linguistics_sentence_reader_ui.py` locally for free-text
reading of any sentence.

## TROPONYM now materialises its HYPONYM/HYPERNYM companion

`TROPONYM` was documented and seeded as one-directional with no
inverse kind, the same category as `ENTAILMENT`/`CAUSE`. That was
wrong: troponymy is verb-specific hyponymy (WordNet models it as the
same hypernym/hyponym relation, just named "troponym" for the narrower
verb) -- "stroll" genuinely *is a type of* "walk", unlike "snore"
